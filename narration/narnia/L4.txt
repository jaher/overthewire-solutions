Narnia, level four. The source declares a two hundred fifty-six byte buffer, wipes every environment string first, then copies argv one into the buffer with strcpy. The wiped environment makes the stack layout the same on every run, so the overflow is deterministic. I log in as narnia four and read the source. The buffer is two hundred fifty-six bytes; main first zeroes every environment string, then, if an argument was given, copies it into the buffer with strcpy. I disassemble main: it subtracts two hundred sixty from the stack pointer, so the buffer sits at ebp minus two hundred sixty, the saved frame pointer at offset two hundred sixty, and the return address at offset two hundred sixty-four. Readelf shows the stack readable, writable and executable, and address randomisation is zero, so a return into the stack will run. In gdb I break at the strcpy call and print the layout. The buffer is at ffff d two a four and the return address slot at ffff d three a c, two hundred sixty-four bytes apart, as expected. Then I write the shellcode in vim. It starts with a write of the four byte marker PWN exclamation, so the address sweep can tell a hit from a crash. The write call itself: one into ebx for standard output, four into edx for the length, syscall four, interrupt eighty hex. Then geteuid, syscall two hundred one, and setreuid with that id twice, syscall seventy, so the effective id survives the exec. Then setuid with the same id, syscall twenty-three, which sets the real, effective and saved ids, so the privilege survives the exec where a plain setreuid would not. Then the execve setup: push a null, push slash slash s h and slash bin slash, point ebx at the path, and start the argument array. The last lines finish it: push ebx, point ecx at the arguments, clear edx, load eleven as the syscall number, and interrupt eighty hex — execve on slash bin slash sh. I assemble it with nasm, check the disassembly with objdump, extract the text section with objcopy, and print the bytes with xxd. Then I write the exploit driver in vim. It loads the shellcode from the assembler output and prints its length in hex; the payload is a NOP sled filling the two hundred fifty-six byte buffer, the shellcode at its end, then four B bytes for the saved frame pointer, then the return address in little-endian. The probe rejects any address whose little-endian bytes contain a null, then runs the binary with the payload, feeding it id and the password read as its standard input. The probe counts a hit when uid equals appears in the output; the sweep runs from ffff d zero zero zero to ffff e eight zero zero, four bytes at a time, and stops at the first hit, printing where it landed. If nothing hits it gives up; otherwise it runs the binary once more at the hit address, feeding it id and the password read on separate lines, and prints whatever comes back. I run the driver: it prints the seventy-eight byte shellcode, sweeps, lands in the NOP sled at 0xffffdc04, the shell comes up as narnia five, and the password prints. The shell runs as narnia five, and the level is solved.
