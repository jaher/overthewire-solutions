Narnia, level four. The source declares a buffer of two hundred fifty-six bytes, wipes every environment string, then copies argv one into the buffer with strcpy. The environment is zeroed first, so the stack layout is the same on every run, and that makes the overflow deterministic. We start with discovery. We list the binary, it is setuid narnia five. We disassemble main with objdump: it subtracts two hundred sixty from the stack pointer, so the buffer is at ebp minus two hundred sixty, the saved frame pointer at offset two hundred sixty, and the return address at offset two hundred sixty-four. We check readelf for an executable stack and confirm it is marked read-write-execute, and we check that address randomisation is zero. In gdb we break at the point just before strcpy and print the buffer address to confirm the layout. Then we write the shellcode in vim: a marker write, then geteuid, then setreuid with the effective id twice, then setuid with the same id, then execve on slash bin slash sh. The setuid call is the lesson of this level. A plain setreuid leaves the saved user id at the unprivileged value, so when execve runs the shell, the kernel drops back to narnia four. Calling setuid with the effective id sets real, effective and saved ids all to narnia five, so the privilege survives the exec. We assemble with nasm, disassemble with objdump, extract the bytes with objcopy, and print them with xxd. Our first attempt placed the shellcode at the end of the buffer, and it crashed. strace showed the marker write, then the two setreuid and setuid calls, and then a segmentation fault, with no execve at all. Disassembling the shellcode explained it: the execve argument pushes write near the top of the buffer, and they overwrote the last instructions of a shellcode that ended there, so the code ran garbage and faulted. The fix is to place the shellcode at the start of the buffer, far below the pushes. We sweep the return addresses, find one that lands in the sled, get a shell as narnia five, read the password and verify by logging in.
