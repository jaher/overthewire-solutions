Narnia, level two. The source shows a character buffer of one hundred twenty-eight bytes, and an unbounded strcpy that copies argv one into it. So any argument longer than one hundred twenty-eight bytes overwrites the saved frame pointer and then the return address. First we inspect the binary. We read the source, then disassemble main with objdump: it subtracts one hundred twenty-eight from the stack pointer and passes the address of ebp minus one hundred twenty-eight to strcpy, so the buffer is at that offset, the saved frame pointer at offset one hundred twenty-eight, and the return address at offset one hundred thirty-two. We check that the stack is executable with readelf, and that address randomisation is off by reading proc sys kernel randomize va space, which is zero. Then we confirm the layout in gdb by breaking right before strcpy returns and printing the buffer and return addresses. Before writing any assembly, we write the payload logic as C and compile it with gcc for thirty two bit. It writes the marker PWN, gets the effective user id, calls setreuid with that id twice, calls setuid with it so the saved user id is updated too, and executes slash bin slash sh. We run the prototype to check the order of the calls is right. Now we translate it to assembly in vim. The key ideas: we clear a register and move a small number into its low byte, so no instruction contains a zero byte, because the argument cannot contain one. The marker is pushed as a four byte value, and slash bin slash sh as two four byte values. We assemble with nasm, disassemble with objdump to see the exact encoding of every instruction, extract the text section with objcopy, and print the bytes with xxd. Then, and this is the important part, we compile a small C harness with gcc that maps an executable page, copies the assembled bytes into it, and calls them. Running the harness shows the bytes print the marker and start a shell. That proves the shellcode itself works before we put it into the overflow. Finally the Python exploit builds the payload: a NOP sled, the shellcode at the end of the one hundred twenty-eight byte block, four bytes of saved frame pointer, and a candidate return address. It forks once per candidate address, redirects output to a pipe, and watches for the marker. When it finds the address, it re-execs attached to the terminal. We get a shell as narnia three, read the password, and verify by logging in.
