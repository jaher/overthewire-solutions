Narnia, level two. The source shows a character buffer of one hundred twenty-eight bytes, and an unbounded strcpy that copies argv one into it. So any argument longer than one hundred twenty-eight bytes overwrites the saved frame pointer and then the return address. First we inspect the binary. We read the source, then disassemble main with objdump: it subtracts one hundred twenty-eight from the stack pointer and passes the address of ebp minus one hundred twenty-eight to strcpy, so the buffer is at that offset, the saved frame pointer at offset one hundred twenty-eight, and the return address at offset one hundred thirty-two. We check that the stack is executable with readelf, and that address randomisation is off by reading proc sys kernel randomize va space, which is zero. Then we confirm the layout in gdb by breaking right before strcpy returns and printing the buffer and return addresses. Next we write the shellcode. We create an assembly file in vim. It writes the marker PWN! to standard output so our address sweep can detect a hit, then calls geteuid, setreuid with that id twice, and finally execve slash bin slash sh. We assemble with nasm, disassemble with objdump to see each instruction's bytes, copy the text section out with objcopy, and print the bytes with xxd. The Python exploit builds the payload: a NOP sled, the shellcode at the end of the one-hundred-twenty-eight byte block, four bytes of saved frame pointer, and the candidate return address. It forks once per candidate address, redirects output to a pipe, and watches for the marker. When it finds the address, it re-execs attached to the terminal.
