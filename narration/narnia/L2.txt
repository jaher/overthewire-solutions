Narnia, level two. Main copies argv one into a one hundred twenty-eight byte buffer with strcpy, and there is no length check. I log in as narnia two, change to slash tmp, and read the source. The disassembly shows the buffer at ebp minus one hundred twenty-eight, so the saved frame pointer sits at offset one hundred twenty-eight and the return address at offset one hundred thirty-two. Readelf shows the stack is readable, writable and executable, and address randomisation is zero, so a return into the stack will run. Before writing assembly, I prototype the payload logic in C. The prototype starts with a comment and the headers, then main opens. It prints the marker PWN exclamation, reads the effective id, sets reuid with it twice, sets uid with it, then execs the shell. I compile it with gcc minus m thirty-two, and run it: it prints PWN exclamation and the effective id, so the syscall order is right. Then I write the shellcode in vim. It starts with a write of the four byte marker PWN exclamation, so the address sweep can tell a hit from a crash. The write call itself: one into ebx for standard output, four into edx for the length, syscall four, interrupt eighty hex. Then geteuid, syscall two hundred one, and setreuid with that id twice, syscall seventy, so the effective id survives the exec. Then setuid with the same id, syscall twenty-three, which sets the real, effective and saved ids, so the privilege survives the exec where a plain setreuid would not. Then the execve setup: push a null, push slash slash s h and slash bin slash, point ebx at the path, and start the argument array. The last lines finish it: push ebx, point ecx at the arguments, clear edx, load eleven as the syscall number, and interrupt eighty hex — execve on slash bin slash sh. I assemble it with nasm, format elf thirty-two, extract the text section with objcopy, and print the bytes with xxd. Before the bytes go into argv one, I prove they work on their own. A small C harness maps a page readable, writable and executable, copies the assembled bytes in, and calls them. It starts with a comment and the headers: standard I/O, standard library, string, and sys/mman for the mapping call. Main opens, declares the file pointer, the byte count and the buffer pointer, and checks it got a file name. It opens the file, checks it, and measures its size with fseek and ftell. Then the mapping: four thousand ninety-six bytes, readable, writable and executable, anonymous and private; it reads the file in and prints the loaded bytes in hex. Finally it prints the jump address, calls the buffer as a function, and reports if the shellcode ever returns. I compile it, and run it on the assembled bytes: it loads seventy-eight bytes, jumps in, and the shellcode prints PWN exclamation, so the code is proven before it goes into the overflow. Then I write the exploit driver in vim. It loads the shellcode from the assembler output, and checks it has no null byte and fits in one hundred twenty-eight bytes. The payload is fifty NOPs, then the seventy-eight byte shellcode, then four B bytes for the saved frame pointer, then the return address in little-endian. The probe rejects any address whose little-endian bytes contain a null, then runs the binary with the payload. The probe writes echo PROBE OK to the target's standard input, and counts a hit only if PROBE OK comes back, because the program echoes the payload, which itself contains PWN exclamation, so grepping for the marker would report hits that never ran. The sweep runs from ffff d zero zero zero to ffff e eight zero zero, four bytes at a time, and stops at the first hit. If nothing hits it gives up; otherwise it runs the binary once more at the hit address, feeding it id and the password read, and prints whatever comes back. I run the driver. It hits at ffff d one e eight after one hundred twenty-three probes, runs the shell as narnia three, and the password prints. The shell runs as narnia three, and the level is solved.
