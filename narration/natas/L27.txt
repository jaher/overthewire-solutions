Natas, level twenty-seven. The page is a login form backed by a user table with sixty-four character username and password columns. Registration refuses names that differ from their trimmed form, and it stores only the first sixty-four characters. Login compares the whole string exactly, and then dumps the row whose username equals the trimmed input. I fetch the source and pull out the registration, login, and dump queries. Three quirks combine. First, if we register a name that is sixty-five characters long, ending in a non-space character, the trim check passes, but the insert cuts it to sixty-four characters. So we register the string natas28 followed by fifty-seven spaces and then an x. The stored username becomes natas28 followed by fifty-seven spaces, with our own empty password. Second, MySQL ignores trailing spaces when comparing strings, so the padded name matches that row and the login check passes. Third, the data dump trims the username before querying, which turns our padded name back into natas28, selects the genuine natas28 row, and prints its real password. So I open vim and write the register and login script: The first chunk sets up the imports, the basic auth header, the page URL, and the post helper, which sends a username and password and returns the content of the page. The last chunk registers the padded name and logs in with it, printing the replies. Here is the last chunk. I run it, and the registration creates our padded user, the login succeeds, and the dump prints the genuine natas28 password, and the level is solved. The lesson is that different layers trim, truncate and compare strings in different ways, and mixing those behaviours creates identity confusion.
