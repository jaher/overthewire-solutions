Natas, level thirty. The page is a Perl login form. The source builds the SQL query by concatenating two calls to the database handle's quote function, one for the username and one for the password. I fetch the source, strip the tags, and grep for the query construction. It shows the query built from quote of the username and quote of the password, then prepare and execute. Quote escapes quotes properly, so a normal string injection does not work. But quote takes an optional second argument, the SQL data type. And in Perl, the CGI parameter function returns a list when the same parameter appears more than once. So if we send the password field twice, the first value becomes the string to quote and the second value becomes the type. I send the password twice: first the injection, OR 1=1, then the value 4. Four is the DBI constant for integer. When quote is told the value is an integer, it does not quote it at all. So the injection is spliced into the query as raw SQL. The condition is true for every row, and the first row, the natas31 account, is printed. Then, for contrast, I send the same injection as a single password value. As a string it is escaped, and the login fails. The lesson is that a safe escaping function can be made unsafe by controlling its extra arguments, and that a list where a scalar was expected is a classic type confusion.
