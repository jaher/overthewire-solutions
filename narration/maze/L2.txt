Maze, level two. The goal is the maze3 password, from /maze/maze2: a setuid maze3 binary that takes one argument and copies its first eight bytes into a twelve-byte buffer whose address is the function pointer, then calls the buffer. The stack is executable and address randomization is off. I log in as maze two and read the binary: the disassembly shows the argc gate, the strncpy of eight bytes into the buffer, and the call through the buffer's own address, so the eight copied bytes execute as code. The mechanism was measured live last session: a breakpoint instruction in the argument lands in the executed buffer and traps. The puzzle from last session is now diagnosed: the pass-reading shellcode pushed its path dwords in forward order, so the stack held the string backwards and the open failed with no such file, which is why its output was empty; and the marker shell's spawned dash drops the elevated identity, so the shell it produced could not be seen reading the file. The fix is to read the file inside the shellcode itself, before any exec, with the path dwords pushed in reverse chunk order so the stack holds the string forwards. I type the corrected shellcode in vim: push the null, then a z e three, s s slash m, e underscore p a, slash m a z, slash e t c, move the stack pointer into the base register, open, read into a stack buffer, write the count to standard output and standard error, exit. It assembles to seventy-one bytes with no null bytes. Then the driver: an environment sled of two thousand A's with the shellcode at the end, and a sweep that builds a six-byte jump instruction for every target address from the low stack upward, runs the level, and stops when anything is printed. The sweep hits at zero x f f f f d six e zero and dumps ten characters twice, the two-descriptor signature: the password comes back. I verify it by logging in as maze three: the identity is fifteen thousand three and the password file matches. The level is solved. I log out.
