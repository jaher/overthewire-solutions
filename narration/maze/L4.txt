Maze, level four. We log in as maze four - level three's magic-dword gate paid off - and the goal is the maze5 password. The gate: /maze/maze4, setuid maze5, sixteen kilobytes, dynamically linked. The disassembly around the interesting instructions shows the gate: a read into a buffer at e-b-p minus zero-a-four, then two movzx byte loads from e-b-p minus zero-three-one and minus zero-three-zero, an imul multiplying them, and a compare against a dword loaded from e-b-p minus zero-a-four - the two files' contents cross-multiplied against each other. Gdb filled in the frame last session: the program reads fifty-two bytes into buffer A, seeks to the dword it just read from file bytes twenty-eight to thirty-one - the file's OWN bytes, the ELF header's e-phonoff field - reads thirty-two bytes into buffer B, and passes only if buffer B's dword at offset twelve equals buffer A's bytes seven and eight multiplied, with a file-size cap of one hundred twenty-three bytes. Then it execs our argument. An ELF header passes this gate for free. Bytes seven and eight of the ELF identification are the OS-ABI and ABI-version fields - zero and zero - so the required product is zero. Bytes twenty-eight to thirty-one are e-phonoff, fifty-two for a bare header-plus-program-header file, so the second read starts right at the program header - whose dword at offset twelve is p-paddr, the physical address field the kernel ignores, free to be zero. And a minimal executable is a hundred and twenty-three bytes exactly: fifty-two header, thirty-two program header, twenty-six of code. Where does it run from? /tmp is tmpfs mounted nosuid - a setuid binary copied there loses its bit - so the working directory is /run/screen, root's real filesystem, and a dash copied there with the -p flag will keep the elevated identity the exec gives it. The builder goes in through vi. It packs an ELF header whose identification carries the bytes s-h, nul, dash-p, nul - the strings we need, hidden in the padding - sets e-phonoff to fifty-two so the gate's own seek lands on our program header, and packs one PT_LOAD with p-paddr zero. The twenty-six-byte stub is hand-assembled execve: push a null, push the address of dash-p, push the address of s-h, point e-c-x at that argv, point e-b-x at s-h, zero e-d-x for the null envp, eleven into a-l, and interrupt eight-zero. Python writes the hundred and twenty-three bytes, the assertion pins the size, and the build prints wrote one hundred and twenty-three bytes. xxd shows the file: the ELF magic, the s-h dash-p strings visible in row zero, and the code bytes starting at offset five-zero. The gate accepts it - valid file, executing - and hands us a dash running as maze5: i-d shows u-i-d fifteen thousand four but e-u-i-d fifteen thousand five - the setuid elevation, kept alive by dash minus-p. cat /etc/maze_pass/maze5 reads A-three-eight-four-six-Z-P-J-u-H.
