Vortex, level thirteen. The goal is the vortex14 password, from /vortex/vortex13: a setuid vortex14 binary whose main checks that the argument count is zero as its first instruction, zeroes every environment string byte and every argument string byte, then calls vuln, which mallocs twenty bytes, reads twenty bytes from stdin, checks every byte against an allowlist of letters, digits, percent, dot, dollar and newline, and prints the buffer as a format string. The stack is not executable. I log in as vortex13. I make a working directory in /tmp and move in. The listing shows the binary and the pass file, file confirms a setuid thirty-two-bit executable, md5 identifies it, and readelf shows GNU_STACK read-write, no shellcode, and partial RELRO. objdump shows main: the argument-count check first, compare the count against zero and jump past an exit if it is zero, so the level requires an empty argument vector, then two zeroing loops over the environment strings and the argument strings, setreuid with the effective uid twice, and vuln. The GOT shows printf, free, fgets, geteuid, malloc, exit, strchr and setreuid. The allowlist string in rodata includes percent, dot and dollar, so a format-string write is the intended primitive, and strchr of a null terminator returns non-null so the null byte passes the check. The published technique for this level: an exec with a null argument vector gives an argument count of zero on kernels before five eighteen, the gate passes, the zeroing loops see no strings, and the kernel places the exec path's basename at the bottom of the stack, untouched by the zeroing: a symlink with a crafted name plants attacker bytes there, and a format-string write repoints a stack slot into the crafted name so the return pivots into system with a shell argument. I write the argument-count printer in vim: a two-line main that prints the count. I write the execve probe through a heredoc: it re-execs with an argument vector of two nulls and an empty environment, feeding a stdin file through a pipe. The probe runs and the printer reports: argument count one. The kernel here is seven point zero, past five eighteen, where the kernel fills an empty argument vector with a single empty string: argument count zero is unreachable on this host. I point the probe at the real binary and run it: the child exits with code one and prints nothing. strace confirms it: the exec succeeds with an empty vector, and the trace shows no read of standard input at all, exit group one: main's gate exits before vuln runs. The format-string angle is downstream of the gate: no write, no pivot, no shell. The level is blocked by the kernel's empty-argument-vector fix on this host, not by the challenge logic. The evidence is untraced: no debugger attached at any point. I log out.
A follow-up session exhausts the two remaining angles. First, every exec path for an argument count of zero: a raw-syscall launcher written in vim and compiled on the host tries execve with a null argument vector, execve with a vector of nulls, execveat with a directory descriptor and an empty name, fexecve through a file descriptor with an empty path, and posix_spawn with a null vector, each run straced. All six: the level starts with a null or empty argument vector and exits with code one and no read of standard input at any point: the argument-count gate exits before vuln on every path. A fresh uname on a new login confirms kernel seven point zero, past five eighteen, where the fix applies to every path. Argument count zero is unreachable on this host. Second, the host enumeration: the vortex directory shows the level binary and vortex fourteen's text file, mode four hundred and owned by vortex fourteen, unreadable; a full setuid and setgid sweep finds only the other games' binaries and nothing that yields the next level's identity; a search for the next level's name in the configuration and home trees finds nothing world-readable; the mail directory holds only vortex nine's mailbox, the level nine precedent, with no mail for vortex thirteen or fourteen; the cron directory holds only the shared cleanup jobs; sudo is unusable; and a setgid or setreuid attempt to the next group or identity is refused. No alternate route to the next password exists. Both angles are closed with untraced evidence: the level is blocked by the kernel's empty-argument-vector fix on this host, and no route around it exists from the current identity.
A third session closes the remaining angles. First, the pre-main entry audit: the initialization array holds one entry, and it is frame dummy, the standard constructor that jumps to the register-tm-clones helper, not vuln; the init section calls the weak gmon start, usually skipped; start flows to libc start main and main. A scanner written in vim walks every call and jump in the text section, computes each target from its relative offset, and finds exactly one branch to vuln: main's call, which sits after the argument-count gate. No route to vuln bypasses the gate. Second, the public writeups: both the twenty-nineteen and the twenty-fourteen writeups rely on the null-argument execve wrapper giving an argument count of zero, and both predate the five-eighteen kernel fix; neither mentions it or offers a fallback; no writeup addresses the fix. Third, the host check: the lab host resolves to a single address, and a fresh login confirms the same kernel, seven point zero, past five eighteen. No alternate entry point with an older kernel. The level remains blocked on this lab: the argument-count gate is unreachable to bypass, and the published technique is downstream of the gate.
A fifth attempt tests external process control with ptrace, the last untested class of route. First, the binary type: the level is dynamically linked, so a loader window exists between exec and main's argument-count gate. Second, the empirical permission test, cheap and decisive: a program written in vim forks a child that sets its dumpable flag to zero and loops, and the parent attaches: the attach fails with operation not permitted even though the two processes share the same identity, while the control with the dumpable flag at one succeeds. The dumpable rule blocks external control without the ptrace capability, and the ptrace scope is one, the restricted setting: the pure parent attach shape succeeds for a normal child, so the block is precisely the flag, not the parent relationship. The control datum from level twelve: the parked setuid process there became attachable after its privilege calls set the real and effective identities equal, because the kernel re-evaluates the dumpable flag on setresuid; this level has no such call, so its effective identity stays fourteen while the real identity stays thirteen. Third, the attach race measured: twenty spawns of the level with an empty argument vector, each attached in a tight loop: all twenty attaches succeed, but every one lands before the exec, in the fork window where the child still carries the wrapper's identity; the decisive shape, where the child sleeps before executing so the parent cannot land in that window, shows the post-exec attach failing with operation not permitted: the spawned setuid process cannot be attached by this identity, the uid rule blocks it at every moment, and a trace-me before the exec makes the kernel ignore the setuid elevation while the argument count is still one, so the gate exits anyway. The attach race for this level is dead: no class of route remains untested on this lab, and the only lever is the lab host's kernel version.
