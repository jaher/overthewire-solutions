Behemoth, level one. The binary declares a character buffer of sixty-seven bytes and calls gets on it. gets reads until a newline with no bound, so this is a classic stack overflow. We inspect the protections first: the stack is marked executable, and address randomisation is off. That combination means we do not need a complicated return-to-libc chain; we can simply place shellcode on the stack and jump to it. We disassemble main with objdump to find the buffer. The buffer is at ebp minus sixty-seven, so the saved frame pointer sits at offset sixty-seven and the return address at offset seventy-one. We confirm this in gdb by breaking right after gets and printing the buffer and return addresses. Then we write the shellcode in assembly. It writes a marker so our sweep can detect a successful jump, then calls geteuid, setreuid with that id twice, setuid with the same id so the privilege survives the exec, and finally execve on slash bin slash sh. We assemble it with nasm, disassemble it with objdump, extract the raw bytes with objcopy and print them with xxd. The payload is seventy-one NOP bytes, then the candidate return address, then the shellcode, then a newline. The exploit forks once per candidate address, feeds the payload on standard input, and watches for the marker. When it finds the address that lands in the shellcode, it runs the binary again with that address and feeds the shell commands. We get a shell as behemoth two, read the password and verify it by logging in.
