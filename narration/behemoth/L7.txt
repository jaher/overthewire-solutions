Behemoth, level seven, the final level. We log in as behemoth seven and look at the binary. The disassembly shows the program copies our first argument into a stack buffer of five hundred twenty-four bytes, but first it runs a filter. The filter walks the argument character by character and refuses anything that is not a letter or a space, and it stops after five hundred twelve characters, while the copy does not stop there. We inspect the protections: readelf shows the stack is marked executable, and address randomisation is off. We probe it: four letters pass, but a percent sign is refused with the message non-alpha chars found in string, possible shellcode. So we send five hundred twelve letters to satisfy the filter, and then we append the real payload: the saved frame pointer, the return address, and our shellcode, none of which the filter ever inspects. The buffer sits five hundred twenty-four bytes below the saved frame pointer, so the return address is at offset five hundred twenty-eight. Then we write the shellcode in vim. It prints a marker so our sweep can detect a successful jump, then raises the effective uid with geteuid and setreuid, and setuid so the privilege survives the exec. And finally execve on slash bin slash slash sh, with a double slash to keep the pushed string aligned. We assemble it with nasm, extract the raw bytes with objcopy, and print them with xxd: seventy-eight bytes. Because the stack address depends on the environment, the exploit sweeps a range of return addresses and looks for the marker the shellcode prints. It lands in the shellcode, we get a shell as behemoth eight, and it prints the final password, and the level is solved. Behemoth is complete: the lesson is that a filter and the operation it protects must cover exactly the same data.
