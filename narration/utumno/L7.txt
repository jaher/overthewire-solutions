Utumno, level seven, the final level. The vulnerable function declares a buffer of zero x one hundred twenty bytes. It stores the address of the buffer plus zero x eighty in a global, calls setjmp on that address, copies the argument into the buffer with strcpy, and then calls longjmp on the same address. The jump buffer lives inside the buffer, so the copy overwrites the saved context. In this glibc the layout is ebx, esi, edi, ebp, esp and eip at offsets zero, four, eight, twelve, sixteen and twenty. The trick is the payload length. If we send one hundred forty one bytes, strcpy writes its terminating null at buffer one hundred forty one, which is the second byte of the saved ebp, and longjmp restores a corrupted frame pointer. Gdb showed exactly that: the frame pointer came back as zero x f f f f zero zero five c. With one hundred forty four bytes the terminator lands at buffer one hundred forty four, which is only the low byte of the saved stack pointer, and longjmp does not need that. The saved ebp at buffer one hundred forty is ours, so longjmp restores it to the buffer address, and then the function's leave and ret read buffer zero as the new frame pointer and buffer four as the return address. Both are ours. We write the shellcode in vim: a marker, the user id calls, and then open and read the utumno eight password file. We assemble with nasm and extract with objcopy. The exploit fills one hundred forty four bytes: the fake frame pointer at zero, the return address at four pointing eight bytes into the buffer, the shellcode at eight, and the frame pointer the jump restores at one hundred forty. It runs the target with that payload and reads the marker and the password, two b v I T u q z N four. Logging in as utumno eight prints the congratulations text, and Utumno is complete.
