Utumno, level one. The binary takes a directory argument, walks its entries, and for any entry whose name begins with s h underscore it calls a function that copies the name into a writable executable page and jumps into it. So the file name is the payload. Two constraints follow. A file name cannot contain a slash, so the shellcode cannot push slash bin slash sh as the usual pair of immediate values. And the copy is strncpy with a large count, which stops at a null byte, so the shellcode cannot contain a zero either. We read the disassembly to confirm the flow. Main calls mmap with protection seven, which is read, write and execute, keeps the address in a global, opens the directory, compares the entry name with the three bytes s h underscore, and calls the runner with the name plus three. The runner copies the string into the mapped page and calls it. So execution starts at the fourth character of the file name. We write the shellcode in vim with those constraints in mind. Slash is never stored as an immediate. We load a dot, which is forty six, and increment it to get forty seven, the slash. Every other byte of slash bin slash sh is loaded into the low byte of a register and stored to the stack. Syscall numbers are loaded with mov al so no instruction contains a zero. The code raises the user id with setreuid and then setuid, so the shell keeps the effective id across execve. A plain setreuid leaves the saved id at utumno one and the shell would drop back. We assemble with nasm, extract the text section with objcopy, and print the bytes with xxd. A small python check prints the length, eighty six, and confirms no slash and no null. Then the exploit creates a directory, removes any old entries, and creates a file whose name is s h underscore followed by those eighty six bytes. Running the binary on that directory executes the shellcode, and the password for utumno two is printed. We verify by logging in.
